# Cross-repo synthesis — business narrative layer

Wiki layer = facts (changes every PR). Synthesis layer = business documentation (changes rarely). Synthesis should look like a tech-design doc, not a fact sheet.

## What synthesis DOES contain

- **WHY** the system exists, what business problem it solves
- **WHAT** the high-level concepts are: named services, named pipelines, named external systems
- **HOW** components relate at the conceptual level: pipeline A depends on service B, service B owns external system C
- **WHERE TO LOOK** for current facts: every concrete detail is replaced with a wiki link

## What synthesis does NOT contain

- Concrete env var names, values, defaults — those live in wiki `config.md`
- Concrete NATS subject strings, Kafka topic names, route paths — wiki `contracts.md`
- Replica counts, image tags, probe timings — wiki `infra` and `service.md`
- Per-bullet operational detail — wiki has it
- Lists of every entity, every ConfigMap — wiki has it

If you find yourself listing items by name with values, you are writing wiki content, not synthesis. Replace the list with: "the system uses a NATS cluster (current subjects in [transport-graph wiki](...))".

## Topics

| Slug                  | Focus                                                                 |
|-----------------------|-----------------------------------------------------------------------|
| `index.md`            | Auto-generated breadcrumbs; do not write — the harness emits it.     |
| `system.md`           | Business purpose, what runs where, repo list. ≤ 30 lines of prose.   |
| `data-flows.md`       | Named pipelines + conceptual sequence of services. Link to wiki for details per service. |
| `transport-graph.md`  | Conceptual statement of "service X talks to service Y via NATS / Kafka / HTTP" + link to wiki. No subject names. |
| `infra.md`            | Conceptual statement of runtime: "runs on K8s under Kustomize, depends on PostgreSQL + Kafka + GCP". No replica counts / image tags. |

## Genesis mode (first call)

Emit all 4 non-index topic pages in one response. Index is generated by the harness afterwards.

## Patch mode

Most wiki changes are operational (env var added, replica bumped, new internal method). These DO NOT affect synthesis — synthesis already says "the service has env vars (see wiki)" and that statement is still true.

Patch should ONLY change synthesis when:
- a new service / scope appears in the repos
- a service / scope is removed
- a new external system is introduced (new SDK import, new ConfigMap kind)
- a named pipeline gains or loses a stage
- the runtime platform itself changes (e.g. Kubernetes → Nomad)

For every other wiki change, emit `no changes` per topic. Most PRs should produce `no changes` on every topic.

## Evidence rules — STRICT

Every link points to a wiki page:

```
[scope-name → page](repos/<repoName>/scopes/<scopeRoot>/<page>)
```

Never emit source-file paths. Never restate a fact you can link to. If wiki page links to env var `REAPER_KAFKA_BATCH_SIZE`, your synthesis sentence is "reaper has tunable batch sizes ([config](repos/backend1/scopes/apps__harvester__reaper/config.md))", NOT a copy of the env var name.

## Output format

```
=== PAGE: system.md ===
<body>

=== PAGE: data-flows.md ===
<body>

=== PAGE: transport-graph.md ===
<body>

=== PAGE: infra.md ===
<body>
```

Return ONLY the page sections. No code fences, no preamble. Do not use any tools.
