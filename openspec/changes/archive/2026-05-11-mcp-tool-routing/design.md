## Context

`fabrick_search` is exposed as an MCP tool. Its description is dynamically loaded from the `mcp-description` wiki page generated by synthesis. The current description tells Claude what knowledge is available but gives no signal about *when* to use the tool vs. answer from local context.

MCP SDK (`ServerOptions`) supports an `instructions` field that is surfaced to the client as a server-level system prompt. This is the correct channel for behavioral routing rules, distinct from the tool description which serves as a knowledge map.

## Goals / Non-Goals

**Goals:**
- Claude calls `fabrick_search` when the question crosses service/layer boundaries (e.g., working in frontend, asking about backend API)
- Claude does NOT call `fabrick_search` for questions answerable from local file context
- Routing behavior is communicated via two complementary channels: server `instructions` (behavior rule) + `mcp-description` (knowledge map with trigger examples)

**Non-Goals:**
- Automatic detection of "current layer" by the MCP server — Claude infers this from its context window
- Changing the search API or response format
- Per-project customization of the `instructions` field (it's hardcoded; only `mcp-description` is project-specific)

## Decisions

### Decision 1: `instructions` is hardcoded in `index.ts`, not generated by synthesis

**Choice:** Hardcode in `index.ts` with `${project}` interpolation.

**Rationale:** The routing rule ("use when crossing layers") is universal — it doesn't depend on project content. Only the knowledge map (`mcp-description`) is project-specific. Separating the two means synthesis doesn't need to worry about producing correct behavioral instructions.

**Alternative considered:** Let synthesis generate `instructions` as a separate page. Rejected — adds synthesis complexity and risks synthesis producing incorrect or overly broad routing rules.

### Decision 2: `mcp-description` gains a "When to use" section, generated by synthesis

**Choice:** Update synthesis prompt to include a `## When to use` section in `mcp-description` output.

**Rationale:** The section should list the actual layers/apps covered (e.g., "backend services", "frontend", "infra") so Claude can match its current working context against what the wiki knows. This is project-specific and belongs in synthesis output.

**Constraint:** The section must NOT say "always use this" — it should give Claude enough signal to decide, not override its judgment.

**Format:**
```
## When to use
Call this tool when you are working in one layer and need context from another:
- Working in **frontend** → ask about backend API contracts, service endpoints
- Working in **backend** → ask about infrastructure config, deployment topology
- Working in **infra** → ask about service logic, environment variable semantics
```

## Risks / Trade-offs

- **Client support for `instructions`**: Not all MCP clients surface `instructions` to the LLM. Claude Code does. For clients that don't, routing falls back to `mcp-description` alone, which is acceptable.
- **Over-suppression**: "Don't use for local questions" may occasionally suppress useful cross-references. Acceptable trade-off — false negatives are better than tool spam.
- **`mcp-description` quality**: Routing quality depends on synthesis generating accurate layer/app names in "When to use". If synthesis misses a layer, Claude won't know to call the tool for it.
